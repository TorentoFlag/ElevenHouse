# Раздел Отзывы: продуктовая спецификация

## Цель

Сделать production-раздел `Отзывы` для ElevenHouse. Клиент может оставить отзыв после получения любого продукта или услуги, отзыв проходит модерацию, после одобрения публикуется на direct-link странице астролога и влияет на рейтинг. Астролог может видеть отзывы, запрашивать отзывы, отвечать на отзывы, использовать AI-черновик ответа и открывать спор.

Раздел не должен превращать ElevenHouse в маркетплейс, каталог, discovery, рекомендации или cross-promo. Отзывы существуют только в контексте конкретного астролога и явной связи клиент-астролог.

## Принятые продуктовые решения

- Отзывы должны быть доступны по каждому продукту ElevenHouse после того, как клиент получил продукт или услугу.
- Нельзя открывать право на отзыв только по факту оплаты. Для каждого продуктового контура нужно доказательство получения, оказания или активного периода услуги.
- Обычное окно для отзыва: 14 дней после получения продукта или услуги.
- Для AstroCalendar окно для отзыва длится весь срок действия услуги и 14 дней после окончания.
- Для AstroDiary paid period применяется обычное окно: 14 дней от server-side activation/entitlement receipt. Более длинное period-window правило не добавляется без отдельного продуктового решения.
- Для pack default policy: отзыв открывается на каждую завершенную сессию пакета. Один отзыв на весь пакет возможен только при отдельном `pack_completed` receipt.
- Для course default policy: отзыв открывается от server-owned course access grant. Completion-based отзыв возможен только при отдельном server-owned completion receipt.
- Для gift default policy: отзыв оставляет фактический получатель подарка, а не покупатель.
- Если после публикации отзыва по заказу или услуге происходит partially_refunded/refund/chargeback, уже опубликованный отзыв остается как есть. Reversal не скрывает опубликованный отзыв, не отправляет его на повторную модерацию и не меняет его статус сам по себе.
- Клиент может редактировать опубликованный отзыв.
- При редактировании новая версия уходит на модерацию, старая одобренная версия остается публичной до одобрения новой.
- Если новая версия отклонена, публичной остается старая одобренная версия.
- Клиент может опубликовать отзыв без публичного имени.
- Публичное имя для такого режима: `Секретный пользователь`.
- В админке модератор видит реального клиента, все версии, историю и служебные данные.
- Астролог и публичные посетители не видят реального клиента для отзывов с режимом `Секретный пользователь`.
- Ответы астролога проходят модерацию.
- Редактирование ответа астролога тоже создает новую версию на модерации, старая одобренная версия ответа остается публичной до одобрения новой.
- Открытие спора сразу скрывает отзыв из публичной проекции и создает moderation case.
- Скрытие при споре является временным состоянием на время проверки, а не финальным удалением.
- AI-черновик ответа входит в production scope.
- AI создает только черновик. Астролог должен отредактировать или подтвердить текст и отправить ответ на модерацию.
- Модератор должен иметь возможность писать клиенту и астрологу из moderation case.

## Участники

- Клиент: оставляет, редактирует и при необходимости публикует отзыв без публичного имени.
- Астролог: видит свои отзывы, запрашивает отзывы, пишет ответы, использует AI-черновики, открывает споры.
- Модератор/admin: проверяет отзывы и ответы, ведет споры, пишет клиенту и астрологу, оставляет внутренние заметки, принимает решения.
- Публичный посетитель: видит только одобренные публичные отзывы на direct-link странице астролога.
- Система/воркеры: создают право на отзыв, отправляют уведомления, поддерживают агрегаты рейтинга, создают разрешенные события.

## Право оставить отзыв

Клиент может оставить отзыв только когда платформа может доказать, что клиент получил продукт или услугу.

Обязательные условия:

- клиент имеет явную связь с астрологом;
- продукт, заказ или услуга относятся к этому астрологу;
- клиент купил или валидно получил продукт/услугу через ElevenHouse;
- продукт или услуга получены, доставлены, завершены или находятся в активном оплачиваемом периоде по authoritative lifecycle этого продуктового контура;
- заказ/услуга не отменены, не partially_refunded/refunded/chargeback, не истекли до получения, не invalidated и не находятся в другом состоянии, запрещающем отзыв;
- окно для отзыва еще открыто;
- по этому экземпляру продукта/услуги нет активной новой версии отзыва на модерации.

Архитектура должна составить карту всех текущих продуктовых контуров:

- live bookings/sessions;
- платные продукты;
- материалы и non-live deliverables;
- AstroCalendar;
- AstroDiary paid periods, если текущий код связывает их с reviewable lifecycle;
- другие продуктовые контуры, найденные в коде.

Для каждого контура нужно определить:

- что является reviewable instance;
- какой ID доказывает конкретный экземпляр услуги или продукта;
- где находится факт получения/оказания/активного периода;
- от какой даты считается окно отзыва;
- какие negative states запрещают отзыв;
- что происходит при partially_refunded, refund, chargeback, cancellation, no-show или expiry.

Если partially_refunded, refund или chargeback происходит после публикации отзыва, опубликованный отзыв остается как есть. Новые отзывы по уже invalidated/partially_refunded/refunded/chargeback состояниям не открываются, но ранее опубликованный отзыв не меняется автоматически.

Если у продукта нет надежного production lifecycle для факта получения, это не повод делать отзыв по факту оплаты. В таком случае prerequisite этого продуктового контура входит в scope Reviews delivery: сначала нужно реализовать доказуемый received/delivered lifecycle, затем открыть отзывы.

## Версии отзывов

Отзывы версионируются.

Публично показывается последняя одобренная версия, если отзыв не скрыт.

При редактировании:

1. Существующая одобренная версия остается публичной.
2. Создается новая версия на модерации.
3. Модератор проверяет новую версию.
4. Одобрение заменяет публичную версию.
5. Отклонение оставляет старую публичную версию без изменений.

Версия отзыва хранит:

- оценку;
- текст;
- режим публичного имени;
- время отправки;
- автора;
- статус модерации;
- решение модерации;
- модератора;
- причину и audit record.

Изменение режима публичного имени также проходит через версию отзыва и модерацию.

## Публичное имя клиента

Для обычной публикации:

- показываем имя, фамилию и аватар;
- если аватара нет, показываем первые буквы имени и фамилии;
- если фамилии нет, показываем первые две буквы имени.

Для публикации без публичного имени:

- публичный посетитель видит `Секретный пользователь`;
- астролог видит `Секретный пользователь`;
- админка видит реального клиента и выбранный режим публикации.

UI должен честно объяснять клиенту границы такого режима: имя и фото скрываются, но текст, редкий продукт или контекст услуги могут косвенно раскрыть автора. Для поверхностей астролога и public page нужно минимизировать лишние подсказки: не раскрывать точный order/session id, служебные детали и избыточный контекст.

Астролог видит полный контекст услуги или продукта, к которому относится отзыв. При публикации без публичного имени скрываются только identity-поля клиента: имя, фамилия, аватар, инициалы и прямые клиентские идентификаторы. Контекст услуги не скрывается.

## Модерация отзывов

Новые отзывы и новые версии отзывов не публикуются до одобрения.

Действия модератора:

- одобрить;
- отклонить;
- скрыть;
- восстановить;
- запросить уточнение у клиента;
- запросить уточнение у астролога;
- оставить внутреннюю заметку;
- закрыть спор.

Каждое решение хранит:

- actor;
- целевой отзыв и версию;
- предыдущее состояние;
- новое состояние;
- reason code;
- optional note;
- timestamp;
- audit entry.

В публичный рейтинг и публичный список входят только одобренные нескрытые версии отзывов.

## Ответы астролога

Ответы астролога проходят модерацию.

Поведение:

- астролог пишет ответ на отзыв;
- ответ отправляется на модерацию;
- до одобрения ответ публично не отображается;
- при редактировании старая одобренная версия ответа остается публичной, пока новая версия на модерации;
- если новая версия ответа отклонена, старая одобренная версия остается публичной;
- если отзыв скрыт, спорный или отклонен, публичный ответ скрывается вместе с ним.

## Споры

Когда астролог открывает спор:

1. Отзыв сразу скрывается из публичной проекции как временно скрытый из-за спора.
2. Создается moderation case.
3. Модератор видит отзыв, публичную версию, pending-версии, историю версий, продукт/услугу, причину спора и контекст.
4. Модератор может написать клиенту и астрологу отдельно.
5. Модератор может восстановить отзыв, оставить скрытым, отклонить pending-версию, одобрить pending-версию или закрыть спор.

Открытие спора требует:

- обязательную причину;
- idempotency;
- audit;
- защиту от duplicate active dispute;
- rate limits или abuse signals для повторных необоснованных споров;
- понятный status `Спор открыт` для астролога;
- priority/SLA для модерации.

Восстановление возвращает отзыв в публичную проекцию с audit note и без потери старой одобренной версии.

## AI-черновик ответа

AI-черновик ответа является production-функцией.

Правила:

- AI создает только черновик;
- AI не отправляет и не публикует ответ без действия астролога;
- астролог может отредактировать черновик перед отправкой;
- отправленный AI-assisted ответ проходит ту же модерацию, что и ручной ответ;
- prompt и provider скрыты от frontend;
- команда генерации идет через backend;
- input в AI должен быть минимальным: текст отзыва, оценка и безопасный публичный контекст;
- real client identity, payment data, moderator notes, case messages и internal audit не отправляются в AI;
- output должен проходить validation/safety rules;
- provider failure и unknown outcome должны быть observable и idempotent.

AI не принимает решения модерации и не влияет на публикацию напрямую.

## Переписка модератора

Для отзывов нужен case-based communication contour.

Он должен поддерживать:

- отдельную переписку модератор-клиент;
- отдельную переписку модератор-астролог;
- ответы сторон в moderation case;
- отдельные visibility правила для каждой стороны;
- внутренние заметки модератора;
- уведомления через outbox/notification worker;
- audit link к отзыву и case.

Клиент и астролог не видят сообщения друг друга. Модератор может отдельно написать summary или финальное решение.

Текущий Messaging нельзя использовать как shortcut, если он не доказывает party-specific visibility. Источник истины для этой переписки должен принадлежать moderation case.

## Раздел отзывов астролога

Раздел астролога показывает:

- средний рейтинг;
- количество отзывов;
- распределение звезд;
- фильтры: все, опубликованные, на модерации, скрытые, спорные;
- карточки отзывов с безопасным product/service context;
- status и version indicators;
- статус ответа;
- AI-черновик;
- ответ;
- спор;
- запрос отзыва.

Reference: `ElevenHouseDesign/app/reviews.jsx` и `ElevenHouseDesign/app/mobile-reviews.jsx`. Production-only состояния нужно добавить отдельно: версии, публикация без публичного имени, модерация ответов, споры, AI, переписка модератора.

## Клиентский кабинет

Клиент видит:

- продукты/услуги, по которым можно оставить отзыв;
- сколько времени осталось на отзыв;
- форму отправки отзыва;
- выбор публикации без публичного имени;
- текущий опубликованный отзыв;
- новую версию на модерации;
- статус модерации;
- объяснение отклонения, если оно должно быть клиент-facing;
- состояние истекшего окна отзыва;
- состояние ожидания подтверждения получения, если продукт еще не reviewable.

## Public page астролога

Публичная direct-link страница астролога показывает:

- средний рейтинг;
- количество отзывов;
- распределение звезд;
- список одобренных отзывов;
- модальное окно всех отзывов;
- фильтры по рейтингу;
- одобренные ответы астролога.

Она не раскрывает:

- pending content;
- rejected content;
- hidden/disputed content;
- moderation reasons;
- реального клиента для `Секретный пользователь`;
- internal IDs;
- audit details.

## Admin/moderator surfaces

Админка содержит очереди:

- новые отзывы;
- новые версии отзывов;
- ответы астролога;
- новые версии ответов;
- споры;
- ответы на запросы уточнения.

Модератор видит:

- реального клиента;
- астролога;
- режим публичного имени;
- связанный продукт/услугу/заказ/сессию;
- активную публичную версию;
- pending-версию;
- историю версий;
- историю спора;
- переписку с клиентом;
- переписку с астрологом;
- внутренние заметки;
- audit timeline.

## Связи с модулями

Отзывы связаны с:

- аккаунтами и ролями;
- клиентскими профилями;
- профилями астрологов;
- связями клиент-астролог;
- продуктами;
- заказами;
- оплатами;
- booking/session lifecycle;
- AstroCalendar;
- AstroDiary paid periods, если они являются reviewable contour;
- public page астролога;
- агрегатами рейтинга;
- admin moderation;
- audit;
- notification/outbox;
- Flow Builder;
- AI provider boundaries;
- case-based moderation communication.

## Flow semantics

Flow должен срабатывать один раз при первой одобренной публичной публикации отзыва.

Техническое имя события: `review_first_published`.

Человеческое название в интерфейсе для астролога: `Отзыв опубликован`.

Событие не должно повторно срабатывать при:

- редактировании;
- одобрении новой версии;
- отклонении версии;
- скрытии;
- восстановлении;
- споре;
- ответе астролога.

Если нужен отдельный automation на pending submission, это отдельное internal/moderation событие, не marketing/CRM Flow trigger.

## Design parity requirements

Нужно снять и сравнить:

- desktop reviews section астролога;
- mobile reviews section астролога;
- request-review modal;
- public reviews section;
- all-reviews modal;
- client review entry and submission states;
- admin moderation queue;
- production-only состояния: версии, скрытое публичное имя, moderation reply, disputes, AI draft, clarification messages, expired review window.

UI acceptance требует browser-backed reference comparison на desktop и mobile.

## Командный процесс

1. PM/BA фиксирует product spec и business flows.
2. Архитектор делает repository trace, external research и architecture plan.
3. Дизайнер готовит state map и недостающие production states.
4. Разработчик реализует через тесты.
5. Сеньор ревьюит архитектуру, безопасность, privacy, moderation, data integrity, idempotency и edge cases.
6. QA проверяет полный production flow.
7. Придирчивый дизайнер проводит финальный visual parity review и блокирует грубый перенос UI.

## Debate loop

Перед implementation planning команда проводит спор:

1. Каждая роль дает независимую позицию.
2. Каждая роль критикует позиции остальных.
3. Каждая роль отвечает на критику.
4. PM/BA фиксирует consensus, измененные решения, unresolved conflicts и решения пользователя.
5. Архитектурный implementation plan начинается только после принятия consensus.
