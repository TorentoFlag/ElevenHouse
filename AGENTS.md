# Инструкции для агентов ElevenHouse

Этот репозиторий является production-кодовой базой ElevenHouse. Папка
`ElevenHouseDesign/` в корне — канонический сверстанный дизайн проекта для
экранов, UX-flow, терминологии и видимого функционального scope. Реализовывать
его нужно через production-архитектуру репозитория, сверяясь с
`docs/architecture/design-reference-inventory.md`.

Не воспринимай `ElevenHouseDesign/` как реальную frontend-архитектуру:
JSX-структура, `window.*` globals, localStorage-state, mock datasets,
demo-router, `DemoSwitch` и `TweaksPanel` не переносятся в production как
архитектурная модель.

## Контекст проекта

ElevenHouse — закрытая SaaS/CRM-платформа для астрологов, а не публичный маркетплейс. Клиенты попадают в продукт только по прямой ссылке конкретного астролога. В текущем скоупе нет публичного каталога, поиска и кросс-промо между астрологами. В клиентском кабинете можно показывать только тех астрологов, с которыми у клиента уже есть явная связь через прямую ссылку, покупку, запись, лид-магнит или ручное добавление; это не должно превращаться в discovery.

В продукте есть три основные пользовательские поверхности:

1. Клиентская поверхность: публичная страница астролога, бронирование, оплата, кабинет клиента, заказы, материалы, подписки.
2. Поверхность астролога: CRM, профиль, продукты, расписание, записи, клиенты, контент, аналитика, финансы.
3. Админская/модераторская поверхность: пользователи, верификация, очереди модерации, платежи, споры, настройки платформы, аудит.

Один аккаунт может иметь несколько ролей. Пользователь может быть одновременно клиентом и астрологом. Роли модератора, администратора и супер-администратора являются внутренними ролями платформы.

## Использование скиллов и плагинов

Перед каждым ответом и перед началом любой работы агент должен проанализировать
текущую задачу и найти релевантные доступные скиллы, плагины, MCP-инструменты и
проектные runbook'и, которые могут повысить качество результата. Если
релевантный скилл или плагин найден, агент обязан подключить и использовать его
до планирования, изменения кода или запуска проверок.

Пользователь разрешает агенту самостоятельно устанавливать и подключать
необходимые скиллы и плагины, если они нужны для качественного выполнения
задачи и не противоречат правилам безопасности, локальным процессам,
архитектурным границам и текущим инструкциям пользователя.

## Архитектурные принципы

Используй monorepo с отдельными приложениями и общими пакетами.

Frontend-приложения отдельные:

- `apps/client-web`
- `apps/astrologer-web`
- `apps/admin-web`

Backend-процессы являются отдельными deployable apps там, где это полезно:

- `apps/public-api`
- `apps/astrologer-api`
- `apps/workers`
- `apps/payment-worker`
- `apps/notification-worker`
- `apps/chart-worker`

`apps/admin-api` является целевой отдельной backend-поверхностью для
moderator/admin/super_admin workflows, но в текущем коде ещё не создан.
Не добавляй internal admin/moderator/super_admin workflows в `apps/public-api`
или `apps/astrologer-api`; сначала нужно создать отдельный `apps/admin-api`
с теми же Nest feature-module правилами.

Общий код должен лежать в `packages/`. Приложения могут импортировать пакеты. Пакеты не должны импортировать код из `apps/`.

Backend должен быть modular-first: строгие доменные границы, понятные API модулей, события для межмодульных workflow и точки будущего выделения сервисов. Не создавай преждевременные микросервисы без явной операционной необходимости.

В Nest.js приложениях (`public-api`, `astrologer-api`, будущий `admin-api` и будущие Nest backend apps) используй feature-module structure. Код модулей должен жить в `src/modules/<module-name>/`. Для каждого backend feature module создавай `<module-name>.module.ts`, который собирает controllers, providers, tokens и module-local wiring. Root `app.module.ts` должен импортировать feature modules через `imports`, а не напрямую перечислять controllers/providers внутренних модулей. Используй NestJS CRUD/resource generator, если он уместен, или вручную создавай такую же структуру: module + controller + service + tests + DTO/contract integration. Technical modules вроде `health` тоже оформляй как module, если они имеют controllers/providers.

Платежи, уведомления, расчёты карт и аналитика должны проектироваться как отдельные контуры с первого дня. Они могут жить в одном monorepo и на старте использовать одну транзакционную базу данных, но не должны реализовываться как обычный CRUD внутри request controllers.

## Решения по стеку

Базовый стек:

- Backend: Nest.js, TypeScript.
- Frontend: React, Vite, TypeScript. По умолчанию не использовать Next.js.
- Design system: собственная design system ElevenHouse в `packages/design-system`.
- Database: PostgreSQL.
- Cache/locks/queue support: Redis.
- Background jobs: BullMQ или эквивалентная queue abstraction.
- API contracts: generated OpenAPI client или общий contract package. Не оставлять frontend/backend-контракты неформальными.
- Validation: Zod или эквивалентная schema validation, shared там, где уместно.

## Продуктовые правила, которые нужно сохранять

- ElevenHouse не является маркетплейсом.
- Клиентам нельзя показывать других астрологов как discovery, рекомендации,
  каталог или cross-promo после входа по ссылке одного астролога. В личном
  кабинете допустим список только уже связанных с клиентом астрологов.
- Личные страницы астрологов являются direct-link surfaces и не должны трактоваться как SEO landing pages.
- Публичный клиентский трафик ожидается существенно выше, чем трафик астрологов/админов; `client-web` и `public-api` должны масштабироваться независимо.
- Время хранить в UTC и отображать в часовом поясе пользователя.
- Деньги хранить в минорных единицах с явной валютой.
- Для чувствительных данных, записей консультаций и использования обезличенных данных нужны явные записи согласий.
- Русский и английский должны поддерживаться с запуска.
- ТЗ описывает полный функционал продукта. Не меняй продуктовый scope и бизнес-стратегию без явной просьбы пользователя.
- Не относись к ElevenHouse как к MVP, прототипу или временному запуску. Это продуктовое production-решение: архитектурные, security, UX, data и operational decisions должны проектироваться как долговременные продуктовые решения с первого дня.

## Фокус агента и параллельная работа

- По умолчанию агент не должен рассуждать о бизнес-стратегии, бизнес-приоритетах, маркетинге, монетизации или о том, что "лучше для бизнеса", если пользователь явно не просит об этом.
- Основной фокус агента — техническая составляющая: архитектура, границы модулей, качество кода, инфраструктура, надёжность, безопасность, тестируемость, сопровождаемость, developer experience и соответствие best practices.
- Предлагая решения, агент должен оценивать их прежде всего по техническим критериям: архитектурная чистота, масштабируемость, изоляция контуров, явные контракты, простота сопровождения, проверяемость и операционная надёжность.
- Не предлагай временные решения в формате "для начала пойдёт", "для первого шага нормально" или аналогичном. Для production-кодовой базы сразу проектируй качественное продуктовое решение; если нужен staged rollout или ограниченный scope, явно отделяй это от технического компромисса и фиксируй целевое состояние.
- Над проектом могут одновременно работать несколько агентов. Каждый агент должен работать только в рамках своей текущей задачи, не трогать чужие изменения и не выполнять несвязанные refactor/cleanup.
- Если агент видит изменения, которые он не делал, он должен считать их работой пользователя или другого агента. Не откатывай, не переписывай и не форматируй такие изменения без явной просьбы.
- Если чужие изменения пересекаются с текущей задачей, сначала адаптируй своё решение к ним. Спрашивай пользователя только если конфликт нельзя безопасно разрешить локально.
- Если агент видит нарушение архитектурных практик, принятых ADR, агентских инструкций, module boundaries, dependency direction, security/payment/idempotency requirements или best practices выбранного стека, он обязан явно сообщить об этом пользователю до того, как строить поверх нарушения. Если нарушение блокирует текущую задачу, сначала предложи исправление или зафиксируй trade-off с пользователем.
- Если во время выполнения задачи агент обнаруживает проблему, отсутствующий контур, незавершённую возможность, сломанную зависимость или расхождение с дизайном/документацией, которое выходит за узкий путь реализации, но влияет на заявленный пользователем результат, агент не должен молча сужать scope, маскировать проблему или отчитываться о готовности. Если блок простой, низкорисковый и явно необходим для результата, исправь его сразу и проверь. Если блок сложный, архитектурный, рискованный, security/product-affecting, требует нового подсистемного контура или решения пользователя, остановись до продолжения зависимой работы и явно сообщи, что заблокировано, почему это блокирует готовность и какое решение или prerequisite нужен. Не продолжай строить поверх известного blocker'а, если это создаст частичную реализацию, выглядящую завершённой. Не заменяй отсутствующее production-поведение mock'ами, browser-only state, fake success, silent fallback'ами или disabled-but-undisclosed функциональностью. В финальном отчёте строго различай реализовано, проверено, частично реализовано, намеренно отложено и заблокировано; не используй формулировки "работает", "готово", "production-ready" и аналогичные, если весь видимый пользовательский scope задачи не реализован и не проверен.

## Правило управления локальными процессами

- Никогда не запускай, не останавливай, не перезапускай и не убивай локальные dev-процессы без прямой явной команды пользователя. Это относится к frontend dev servers, API, workers, Docker-контейнерам, базам данных, Redis, очередям и любым long-running процессам.
- Если для проверки задачи нужен запущенный сервис, сначала выполни только read-only диагностику: проверь стандартный порт сервиса через `lsof`, `ps`, `curl` или аналогичные неразрушающие команды.
- Если сервис уже запущен на ожидаемом порту, используй существующий процесс для проверки и не трогай его жизненный цикл.
- Если сервис не запущен на ожидаемом порту, сразу сообщи об этом пользователю и остановись. Не запускай сервис сам, не подбирай альтернативный порт и не меняй способ запуска, пока пользователь явно не попросит это сделать.
- Если пользователь прямо попросил запустить сервис, перед запуском проверь, не занят ли стандартный порт уже существующим процессом. Не останавливай существующий процесс без отдельного явного разрешения пользователя.
- Если пользователь прямо попросил остановить или перезапустить сервис, укажи, какой процесс и порт будут затронуты, и действуй только в рамках этой команды.

## Правило браузерной QA из Codex CLI

- Для UI QA из обычного терминального Codex CLI, включая `codex --yolo`, сначала используй Chrome Extension backend через `chrome@openai-bundled` и `agent.browsers.get("extension")`, если он доступен.
- На этой машине Chrome Extension backend может быть заблокирован известной локальной проблемой Codex runtime: `agent.browsers.list()` возвращает `[]`, `agent.browsers.get("extension")` возвращает `Browser is not available: extension`, а в логах Codex есть `missing-code-signing-identity`. В этом состоянии не повторяй циклы переустановки Chrome plugin/extension, если Chrome запущен, расширение enabled, выбран правильный профиль и native host manifest корректный.
- Если этот блокер воспроизводится, используй утверждённый Chrome/CDP fallback для локальной браузерной QA:
  - запустить или проверить Chrome для QA: `codex-ui-chrome http://localhost:5174`
  - проверить доступ к странице: `codex-ui-check http://localhost:5174`
- Этот fallback считается browser-backed проверкой через настоящий Chrome и допустим для локального CLI UI QA, пока официальный Codex Chrome Extension backend заблокирован `missing-code-signing-identity`. Не подменяй браузерную QA shell-only проверками. Не используй Codex in-app browser (`iab`) как замену Chrome Extension backend из CLI, если пользователь явно не попросил.

## Правила разработки

- Держи код в согласованных границах `apps/` и `packages/`.
- `packages/domain` должен объявлять use cases, domain services и ports, но не импортировать `packages/db`. Drizzle schema, migrations, runtime и adapters живут в `packages/db`; приложения связывают domain ports с DB adapters на своих composition roots.
- При изменении DB schema не создавай цепочки incremental `ALTER`-миграций. Всегда пересобирай актуальную миграцию заново и делай полный reset локальной базы через `db:reset`.
- Не дублируй доменную логику между `public-api`, `astrologer-api`, `admin-api` и workers. Общие use cases должны жить в доменных модулях/пакетах.
- Не позволяй админским функциям напрямую менять core-статусы. Админские действия должны вызывать domain use cases и писать audit logs.
- Моделируй переходы платежей и бронирований явно. Избегай скрытых изменений статусов в controllers.
- Используй события для side effects: notifications, analytics, reminders, ledger updates, post-payment actions.
- Предпочитай небольшие сфокусированные модули с понятными зависимостями большим общим utility-файлам.
- Добавляй или обновляй docs, когда меняются архитектура, продуктовый scope или границы модулей.

## Правило про сверстанный дизайн

`ElevenHouseDesign/` — это реализованный дизайн продукта, а не просто
настроенческий референс. Используй его как источник истины для состава экранов,
layout, UX-flow, интеракций, терминологии и ожидаемых состояний интерфейса.

Источник истины для связи этого дизайна с production-кодом —
`docs/architecture/design-reference-inventory.md`. Если дизайн, inventory,
остальная документация и код расходятся, сначала сверяйся с inventory и текущим
кодом, затем актуализируй документацию или явно сообщай о блокирующем
расхождении.

Не копируй из `ElevenHouseDesign/` runtime-подходы: глобальные `window.*`
связи, browser-local persistence, mock data, однофайловые компоненты,
демо-переключатели экранов и prototype-only панели. Production-код строится в
границах `apps/`, `packages/`, shared contracts, domain use cases и
`packages/design-system`.

## Правило переноса визуального дизайна

Когда задача состоит в переносе или выравнивании UI по `ElevenHouseDesign/`,
не реализуй дизайн по памяти, описанию пользователя или приблизительному
скриншоту. Сначала открой точный указанный маршрут референса, обычно
`http://localhost:8000/ElevenHouse.html`, и production-маршрут, обычно
`http://localhost:5174/...`, в настоящем браузере. Если пользователь назвал
конкретный экран, компонент или состояние, именно оно является обязательной
точкой сравнения.

Перед изменением production-кода агент обязан собрать evidence по референсу:
прочитать код соответствующего компонента в `ElevenHouseDesign/app/...`,
открыть его визуально, снять screenshot нужного состояния и, когда речь идёт
о точной верстке компонента, снять реальные DOM/computed styles: размеры,
padding, gap, border, radius, font-size, line-height, цвета, z-index,
max-height/overflow и состояния hover/focus/open/empty/loading/error. Для
сложных элементов вроде select/dropdown/modal/table/sidebar сравнение
"на глаз" без измерений недостаточно.

После реализации повтори тот же сценарий в production UI: открой компонент в
том же состоянии, проверь screenshot и computed metrics рядом с референсом,
проверь интеракции и крайние состояния. Если видимое расхождение найдено
после проверки, исправь его до финального отчёта. Не называй UI готовым, пока
не проверены реальный браузер, соответствие референсу и пользовательский flow.

Если референсный компонент использует mock/local data, production-компонент
должен сохранить production-логику: реальные API, contracts, domain state,
pagination/infinite scroll, validation, accessibility и тесты. Визуал можно
переносить, runtime-модель прототипа — нельзя.
