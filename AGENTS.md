# Инструкции для агентов ElevenHouse

Этот репозиторий является production-кодовой базой ElevenHouse. Отдельную папку с заранее сверстанным дизайном нужно считать только визуальным и продуктовым референсом. Не воспринимай эту папку как реальную frontend-архитектуру, не рефактори её и не строй production-код поверх неё, если пользователь явно об этом не попросил.

## Контекст проекта

ElevenHouse — закрытая SaaS/CRM-платформа для астрологов, а не публичный маркетплейс. Клиенты попадают в продукт только по прямой ссылке конкретного астролога. В текущем скоупе нет публичного каталога, поиска и кросс-промо между астрологами.

В продукте есть три основные пользовательские поверхности:

1. Клиентская поверхность: публичная страница астролога, бронирование, оплата, кабинет клиента, заказы, материалы, подписки.
2. Поверхность астролога: CRM, профиль, продукты, расписание, записи, клиенты, контент, аналитика, финансы.
3. Админская/модераторская поверхность: пользователи, верификация, очереди модерации, платежи, споры, настройки платформы, аудит.

Один аккаунт может иметь несколько ролей. Пользователь может быть одновременно клиентом и астрологом. Роли модератора, администратора и супер-администратора являются внутренними ролями платформы.

## Архитектурные принципы

Используй monorepo с отдельными приложениями и общими пакетами.

Frontend-приложения отдельные:

- `apps/client-web`
- `apps/astrologer-web`
- `apps/admin-web`

Backend-процессы являются отдельными deployable apps там, где это полезно:

- `apps/public-api`
- `apps/ops-api`
- `apps/workers`
- `apps/payment-worker`
- `apps/notification-worker`
- `apps/chart-worker`

Общий код должен лежать в `packages/`. Приложения могут импортировать пакеты. Пакеты не должны импортировать код из `apps/`.

Backend должен быть modular-first: строгие доменные границы, понятные API модулей, события для межмодульных workflow и точки будущего выделения сервисов. Не создавай преждевременные микросервисы без явной операционной необходимости.

В Nest.js приложениях (`public-api`, `ops-api` и будущие Nest backend apps) используй feature-module structure. Код модулей должен жить в `src/modules/<module-name>/`. Для каждого backend feature module создавай `<module-name>.module.ts`, который собирает controllers, providers, tokens и module-local wiring. Root `app.module.ts` должен импортировать feature modules через `imports`, а не напрямую перечислять controllers/providers внутренних модулей. Используй NestJS CRUD/resource generator, если он уместен, или вручную создавай такую же структуру: module + controller + service + tests + DTO/contract integration. Technical modules вроде `health` тоже оформляй как module, если они имеют controllers/providers.

Платежи, уведомления, расчёты карт и аналитика должны проектироваться как отдельные контуры с первого дня. Они могут жить в одном monorepo и на старте использовать одну транзакционную базу данных, но не должны реализовываться как обычный CRUD внутри request controllers.

## Решения по стеку

Базовый стек:

- Backend: Nest.js, TypeScript.
- Frontend: React, Vite, TypeScript. По умолчанию не использовать Next.js.
- Design system: собственная design system ElevenHouse в `packages/design-system`.
- Database: PostgreSQL.
- Cache/locks/queue support: Redis.
- Background jobs: BullMQ или эквивалентная queue abstraction.
- API contracts: generated OpenAPI client или общий contract package. Не оставлять frontend/backend-контракты неформальными.
- Validation: Zod или эквивалентная schema validation, shared там, где уместно.

## Продуктовые правила, которые нужно сохранять

- ElevenHouse не является маркетплейсом.
- Клиентам нельзя показывать других астрологов после входа по ссылке одного астролога.
- Личные страницы астрологов являются direct-link surfaces и не должны трактоваться как SEO landing pages.
- Публичный клиентский трафик ожидается существенно выше, чем трафик астрологов/админов; `client-web` и `public-api` должны масштабироваться независимо.
- Время хранить в UTC и отображать в часовом поясе пользователя.
- Деньги хранить в минорных единицах с явной валютой.
- Для чувствительных данных, записей консультаций и использования обезличенных данных нужны явные записи согласий.
- Русский и английский должны поддерживаться с запуска.
- ТЗ описывает полный функционал продукта. Не меняй продуктовый scope и бизнес-стратегию без явной просьбы пользователя.
- Не относись к ElevenHouse как к MVP, прототипу или временному запуску. Это продуктовое production-решение: архитектурные, security, UX, data и operational decisions должны проектироваться как долговременные продуктовые решения с первого дня.

## Фокус агента и параллельная работа

- По умолчанию агент не должен рассуждать о бизнес-стратегии, бизнес-приоритетах, маркетинге, монетизации или о том, что "лучше для бизнеса", если пользователь явно не просит об этом.
- Основной фокус агента — техническая составляющая: архитектура, границы модулей, качество кода, инфраструктура, надёжность, безопасность, тестируемость, сопровождаемость, developer experience и соответствие best practices.
- Предлагая решения, агент должен оценивать их прежде всего по техническим критериям: архитектурная чистота, масштабируемость, изоляция контуров, явные контракты, простота сопровождения, проверяемость и операционная надёжность.
- Не предлагай временные решения в формате "для начала пойдёт", "для первого шага нормально" или аналогичном. Для production-кодовой базы сразу проектируй качественное продуктовое решение; если нужен staged rollout или ограниченный scope, явно отделяй это от технического компромисса и фиксируй целевое состояние.
- Над проектом могут одновременно работать несколько агентов. Каждый агент должен работать только в рамках своей текущей задачи, не трогать чужие изменения и не выполнять несвязанные refactor/cleanup.
- Если агент видит изменения, которые он не делал, он должен считать их работой пользователя или другого агента. Не откатывай, не переписывай и не форматируй такие изменения без явной просьбы.
- Если чужие изменения пересекаются с текущей задачей, сначала адаптируй своё решение к ним. Спрашивай пользователя только если конфликт нельзя безопасно разрешить локально.
- Если агент видит нарушение архитектурных практик, принятых ADR, агентских инструкций, module boundaries, dependency direction, security/payment/idempotency requirements или best practices выбранного стека, он обязан явно сообщить об этом пользователю до того, как строить поверх нарушения. Если нарушение блокирует текущую задачу, сначала предложи исправление или зафиксируй trade-off с пользователем.

## Правила разработки

- Держи код в согласованных границах `apps/` и `packages/`.
- `packages/domain` должен объявлять use cases, domain services и ports, но не импортировать `packages/db`. Drizzle schema, migrations, runtime и adapters живут в `packages/db`; приложения связывают domain ports с DB adapters на своих composition roots.
- При изменении DB schema не создавай цепочки incremental `ALTER`-миграций. Всегда пересобирай актуальную миграцию заново и делай полный reset локальной базы через `db:reset`.
- Не дублируй доменную логику между `public-api`, `ops-api` и workers. Общие use cases должны жить в доменных модулях/пакетах.
- Не позволяй админским функциям напрямую менять core-статусы. Админские действия должны вызывать domain use cases и писать audit logs.
- Моделируй переходы платежей и бронирований явно. Избегай скрытых изменений статусов в controllers.
- Используй события для side effects: notifications, analytics, reminders, ledger updates, post-payment actions.
- Предпочитай небольшие сфокусированные модули с понятными зависимостями большим общим utility-файлам.
- Добавляй или обновляй docs, когда меняются архитектура, продуктовый scope или границы модулей.

## Правило про дизайн-референс

Существующая папка с дизайном — это референс для визуального направления и продуктовых flow. Используй её, чтобы понимать экраны, layout и терминологию. Не предполагай, что её структура файлов, границы компонентов или state management подходят для production.
